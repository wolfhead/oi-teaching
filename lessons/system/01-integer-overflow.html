数字数到头了会怎样？

一个关于 C++ 整数溢出的小实验 —— 以及一件比"变成随机数"更奇怪的事

1. 先说说数字盒子

在 C++ 里写 int x;，就是跟电脑要了一个固定大小的盒子来装数字。这个盒子有 32 个小格子，每个格子只能放 0 或 1。

32 个格子能表示的数字是有限的。int 能装的最大的数是：

2147483647

大约 21 亿。这个数有个名字叫 INT_MAX。

那再加 1 会怎么样呢？

很多人以为数字是一条直线，一直往右走就行了。但对电脑来说，数字更像一条环形跑道：

2147483645→ 2147483646→ 2147483647→ -2147483648→ -2147483647

走到最大的正数，再往前一步，就绕到了最小的负数。就像老式汽车的里程表，开到 999999 再开一公里会变回 000000。

我们真的跑一下这段程序：

int x = 2147483645;
for (int i = 0; i < 5; ++i) {
  printf("x = %d\n", x);
  x = x + 1;
}

结果：

x =  2147483645
x =  2147483646
x =  2147483647
x = -2147483648   <-- 翻车了！
x = -2147483647
第一个结论：它变成的是一个确定的负数，不是随机数。
每次跑都一样，换台电脑也一样。它不"随机"，它很守规矩。

2. 但是，真正奇怪的事情在后面重点

现在看这段程序。它做了三件事：把 y 打印出来，问 y 是不是比 x 大，再问 y 是不是负数。

int x = 2147483647;   // 最大的 int
int y = x + 1;        // 这里翻车了

printf("y      = %d\n", y);
printf("y > x ? %s\n", y > x ? "true" : "false");
printf("y < 0 ? %s\n", y < 0 ? "true" : "false");

同一份代码，用两种方式编译。-O2 的意思是"让编译器帮我优化，跑得快一点"。

问题不优化（-O0）优化（-O2）
y 是多少？-2147483648-2147483648
y > x ？falsetrue
y < 0 ？truefalse

看右边那一列 —— 在同一次运行里，同一个 y：

  • 打印出来是 -2147483648
  • 但电脑说它 比 21 亿还大
  • 而且说它 不是负数
一个数，同时是负两百多亿、又比正二十一亿大、又不是负数。
它自相矛盾了。

3. 为什么会这样？一个关于承诺的故事

假设你跟妈妈说："我保证我考试从来不会不及格。"

妈妈相信了。于是她想：既然他从不会不及格，那我根本不用检查他的分数，我可以直接跟亲戚说"我儿子成绩很好"，还能省下辅导班的钱。

结果有一次你考了 40 分。

妈妈会怎么样？她不会随机乱说话。她会非常有逻辑地、一本正经地继续说"我儿子成绩很好" —— 因为她是严格按照你给的那个承诺在推理的。

错的不是妈妈的逻辑，是你给的前提。

C++ 里也有一模一样的事。C++ 的规则书里写着一条：

程序员保证：整数永远不会溢出。
（如果溢出了，那这个程序会发生什么，规则书什么都不保证。）

编译器完全相信这个承诺。所以当它看到 y = x + 1 时，它会推理：

"既然溢出不可能发生，那 y 就一定比 x 大 —— 这还用算吗？直接写死答案 true，比较都不用做了，程序跑得更快！"

于是就出现了那个矛盾：

代码在做什么编译器怎么处理得到什么
printf("%d", y)
要一个真实的数字		没办法糊弄，必须真的去算
→ CPU 老老实实做加法		-2147483648
y > x
只是一个判断		用"承诺"推理出答案
→ 加法根本没执行		true

需要真实数字的时候，用硬件算出来的真结果；
只需要下判断的时候，用"不会溢出"这个假设推出来的假结果。

平时这两套是一致的，谁也发现不了。一旦溢出，它们就打起来了。

4. 那这像量子力学吗？

有人会说：这不就像量子嘛 —— 我看它一眼它就有值，我不看它就没有值？

这个联想很聪明，但有个关键区别，搞混了会踩坑：

量子整数溢出
什么时候定下来运行的那一刻
（你测量它的瞬间）		编译的时候
（程序还没开始跑）
会不会每次不一样会，是真随机不会，跑一万次完全一样
什么会改变结果你什么时候观察你用什么编译器、开不开优化

所以更准确的说法是：结果在程序开始运行之前，就已经被编译器全部决定好了。它一点都不神秘，也一点都不随机 —— 只是编译器按照一个错误的前提，做了一堆非常有逻辑的决定。

这其实比量子更麻烦。如果它真是随机的，你多跑几次就发现问题了。
但它是稳定的 —— 在你的电脑上稳定地正确，然后换个编译器、换个优化选项，就稳定地错误。

5. 三句话总结

  1. 不是随机数。 硬件层面它就是绕一圈变成负数，规规矩矩。
  2. 但也别指望它是负数。 C++ 没有答应过你这件事，编译器可能把你的代码整段删掉。
  3. 正确的说法是：溢出之后，整个程序的行为都没有保证了 —— 不只是那一个数字出问题，是程序可以开始自相矛盾。

6. 怎么保护自己

写代码的时候，让电脑帮你抓

编译的时候加上这个魔法咒语：

g++ -fsanitize=undefined 你的程序.cpp -o 程序
./程序

一旦溢出，它会立刻告诉你，还会指出是第几行：

runtime error: signed integer overflow:
2147483647 + 1 cannot be represented in type 'int'

如果真的需要装很大的数

换个更大的盒子 —— long long 有 64 个格子，能装到约 922 京（9 后面 18 个 0）。

如果想自己检查会不会溢出

不要写 if (x + 1 < x) —— 刚才已经看到了，这行会被编译器删掉。要用专门的工具：

int result;
if (__builtin_add_overflow(x, 1, &result)) {
    // 溢出了，在这里处理
}

最后一个冷知识

上面说的都是有符号整数（int，能存负数的那种）。

还有一种叫无符号整数（unsigned int，只能存 0 和正数）。它的溢出规则完全不同 —— C++ 明确保证它会绕回 0，这是合法的、被允许的行为，不是错误：

unsigned int u = 4294967295;  // 最大值
u = u + 1;                    // 保证得到 0，这是规定好的

同样是"数到头了"，一个是严重错误，一个是正常操作。这是 C++ 里最容易搞混的地方之一，记住它你就超过很多人了。

本文里所有的运行结果都是真实跑出来的，不是编的。
你可以自己把代码敲一遍，用 -O0 和 -O2 各编译一次，亲眼看看那个矛盾。
