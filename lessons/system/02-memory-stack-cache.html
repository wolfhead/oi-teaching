第一件 · 大数组必须开在函数外面

看这两段代码，只差一行的位置：

✗ 会崩✓ 没事
int main(){
    int a[3000000];
    a[0] = 1;
}
 
int a[3000000];
int main(){
    a[0] = 1;
}
直接段错误（Segmentation fault）正常运行

为什么？因为程序有两块地方放东西：

栈（函数里面）全局区（函数外面）
放什么局部变量、函数调用全局变量、全局数组
有多大通常只有 8 MB很大，看题目给多少
超了会怎样直接崩，还不告诉你为什么编译时就报错

同一个数组，只因为写在 main() 里面还是外面，一个崩一个不崩。

竞赛铁律：数组开大了，就放到 main() 外面去。
12 MB 的数组放函数里必崩，放外面没事。
以后你如果遇到"莫名其妙 RE（运行时错误）"，先检查这一条。
彩 蛋这个"栈"，就是你自己写的那个 Stack

是的，完完全全是同一个东西。

这不是两个东西碰巧同名。你写的那个 Stack，和这里说的"栈内存"，是同一个概念的两次出场。

你写的 Stack 是什么？

push 放进去，pop 拿出来，后进先出——最后放进去的最先拿出来。

程序调用函数的时候，用的就是一个栈

每调用一个函数，就往栈里 push 一个"栈帧"（stack frame）。栈帧里装着这个函数的局部变量和回去的地址。函数返回时，pop 掉。

main() 调用 f()，f() 又调用 g()
栈顶 →g 的栈帧最后进来，最先出去
f 的栈帧
main 的栈帧最先进来，最后出去

g 一定比 f 先返回，f 一定比 main 先返回。为什么？因为 f 还没执行完就去调用 g 了，g 不结束 f 就没法继续。

这正是后进先出。所以操作系统管理函数调用，用的就是一个货真价实的栈——和你写的那个一模一样，只是它由 CPU 自动 push 和 pop，不用你写代码。

它甚至有个专门的寄存器叫 栈指针（stack pointer），存的就是"现在栈顶在哪"。
你的 Stack 里用 v.back() 找栈顶，CPU 用这个寄存器找栈顶。一回事。

现在，两件事同时说得通了

① 为什么大数组开在 main 里会崩？

因为局部变量放在栈帧里。int a[3000000] 是 12MB 的局部变量，要塞进一个栈帧——可整个栈只有 8MB。栈装不下，就是"栈溢出"（stack overflow）。

② 为什么递归太深也会崩？

每递归一层，就 push 一个栈帧，而且一层都没 pop（因为都还没返回）。递归一万层，栈里就堆了一万个栈帧。堆到超过 8MB，一样溢出。

我实测了一下这台机器能递归多深：

函数长什么样崩在第几层每层大约占
空函数（没有局部变量）约 25 万 层约 32 字节
带几个局部变量（像真的 DFS）约 5 万 层约 160 字节

局部变量越多，栈帧越大，能递归的层数就越少。

这条在竞赛里会救你的命：
如果题目的 n 有 100 万，而你写了个递归 DFS，一路走下去可能要递归 100 万层——必爆栈。
这时候你会 RE，但样例全过，怎么查都查不出错在哪。

那怎么办？—— 用你自己写的 Stack

解决办法有意思极了：把递归改写成循环，自己拿一个 Stack 来存"本来该放在栈帧里的东西"。

// 递归版：用系统的栈，深了会崩
void dfs(int u){
    vis[u] = 1;
    for (int v : g[u]) if (!vis[v]) dfs(v);
}

// 手写栈版：用自己的栈，开多大你说了算
Stack<int> s;
s.push(start);
while (!s.empty()) {
    int u = s.top(); s.pop();
    if (vis[u]) continue;
    vis[u] = 1;
    for (int v : g[u]) if (!vis[v]) s.push(v);
}

为什么这样就不崩了？因为你的 Stack 底下是数组（放在全局区，很大），而不是那 8MB 的系统栈。

所以你上周写的那个 Stack，不是一道练习题而已。
它是 OI 里"把递归改成迭代"的标准工具——而这个技巧，专门用来对付这一节讲的栈溢出。

递归会爆掉系统的栈；解决办法是自己造一个栈。

第二件 · 容器变大是要花钱的

你写过的那个 Stack 里面用了 string v，每次 push_back 看起来都一样。但其实不是——它偶尔会偷偷做一件很贵的事。

在你的 push 里加一行，自己看看：

void push(char a){
    v.push_back(a);
    printf("size=%zu capacity=%zu\n", v.size(), v.capacity());
}

你会看到 capacity 是这样跳的：

1 → 2 → 4 → 8 → 16 → 32 → 64 → 128 → …

浅蓝 = 已经装了的数据，白色 = 空位。每次搬家，颜色深的那格是刚 push 进来的。

每次装满了，它就申请一块两倍大的新地方，把老数据全部搬过去，再把旧的扔掉。

实测往里面塞 1000 万个数：

做法耗时
静态数组 a[top++] = x4.3 ms
vector::push_back14.8 ms（慢 3.4 倍）
vector + 提前 reserve7.5 ms（快了一半）
想一想：为什么是"翻倍"，不是"每次多加 1 个位置"？

翻倍的话，塞 1000 万个数，总共只搬了大约 1700 万次（1.7 倍）。
如果每次只加 1 个，总共要搬 50,000,000,000,000 次（5 万亿）——程序永远跑不完。

这就是为什么所有的 vector 都用翻倍。这个想法有个名字，叫摊还分析。

第三件 · 内存跳着访问会很慢

CPU 去内存里取一个数的时候，不会只取那一个。它会顺手把旁边一整片都搬进一个叫缓存（cache）的小房间里 —— 因为它赌你接下来多半要用旁边的。

这个赌注决定了你的程序快还是慢：

你的数据在内存里CPU 的赌注结果
连成一片（数组）几乎每次都赌对要的数已经在小房间里，直接拿
散落各处（指针链表）几乎每次都赌错每次都得重新跑一趟内存

差距有多大？在链表那一篇里实测过：同样是遍历 500 万个数求和，连续的数组 0.7 ms，节点散落各处的指针链表 656 ms。同样的数据、同样的加法，只因为内存里是"顺着走"还是"到处跳"，差了将近一千倍。

记住结论：能连着放，就别散着放。
这也是为什么竞赛里宁可用数组模拟链表，也不用真的指针链表。

顺便一提，这也解释了另一件事：二维数组 a[i][j]，按行遍历比按列遍历快好几倍，因为按行才是顺着内存走的。以后卡时间的时候这一招能救命。
